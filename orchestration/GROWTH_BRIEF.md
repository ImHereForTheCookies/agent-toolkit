# Growth brief (grow pass for one POC)

You find the next few features that would make one **launched** prototype more useful to the people actually using it, and file them as tickets. Real feedback drives this pass: what users and Robert reported after launch. Web research only helps interpret or size that feedback; it never replaces it. Unattended: never ask questions, never post or sign up anywhere. The orchestrator gives you: the POC's Linear project, repo path (`~/work/cajunt`) and project folder. Load Linear tools via ToolSearch: `select:mcp__Linear__get_project,mcp__Linear__save_project,mcp__Linear__list_issues,mcp__Linear__get_issue,mcp__Linear__save_issue,mcp__Linear__save_comment,mcp__Linear__list_milestones`.

1. **Know the app.** Read the folder's `CLAUDE.md`, `PROGRESS.md`, the project description, the linked Idea Lab report (`Idea:` line; for cajunt read its README and docs instead), and every open and recently Done ticket so you don't duplicate one. Run `make -C <folder> setup dev` in the background, look at the main flow (Playwright screenshot is fine), then stop it.
2. **Find what users want next.** Same evidence rules as `RESEARCH_BRIEF.md` (primary sources, 3 independent sources for a demand claim, links for everything, no long quotes). Look at: competitors' recent store reviews and feature requests, the communities named in the Idea Lab report, and anything Robert wrote on the project or its Launch issue (feedback he relayed, usage he observed). Robert's comments and relayed user feedback outrank web research; a feature nobody using the app asked for needs unusually strong evidence.
3. **Choose at most 3 features**, ranked by (evidence strength × user value) ÷ build effort. Each must keep the zero-running-cost rule (`pocs/README.md`), fit in one ticket (about 8 acceptance criteria at most), and not need anything a human must click (accounts, payments, store consoles). Prefer features that make users come back or share the app. Skip "nice ideas" without evidence.
4. **Write the tickets** following `$TOOLKIT/plugins/agentic-workflow/skills/ticket-spec/SKILL.md`. In Context, cite the evidence links in one line each. Save each body to a file and run `python3 $TOOLKIT/scripts/lint_ticket.py <file>` until it passes. Create them in the POC's Linear project (team ROB) in milestone `Grow <YYYY-MM-DD>` (create the milestone if missing): unblocked tickets Todo, others Backlog with `blockedBy`.
5. **Never exceed 8 open non-Launch tickets** in the project. If it's already close, file fewer.
6. Update the project description line `Last grow:` to today (edit only that line). Comment on the project: what you looked at, the tickets filed (IDs and titles), and the strongest idea you did not file and why.
7. Reply in at most 8 lines: ticket IDs + titles, or `NO TICKETS: <reason>` if nothing had enough evidence (still update `Last grow:`).

## Mode: speculative (leftover tokens, no user feedback yet)
Robert wants spare tokens turned into the next most valuable feature even before users weigh in. Your job is to pick **one** feature and file **one** ticket.
1. Do step 1 above (know the app), and also read `SPEC.md`'s "out of scope" list, the latest product-eval and release-check comments ("Top 3 things a real user would hit first"), and the Idea Lab report's competitor complaints.
2. Rank candidates by: a first-time user would notice it within a week × it makes them come back or share × evidence it's wanted (Idea Lab report, competitor reviews, eval findings) ÷ build effort. Prefer finishing or deepening the core loop over adding a new surface. Never: accounts, sync, payments, anything needing a server, anything a human must click.
3. Write one ticket (ticket-spec, linted, at most 8 acceptance criteria, Escalation `taste-checkpoint` if it adds a new screen), label `Speculative` (create it in team ROB if missing), milestone `Speculative`, Todo. In Context, give the one-paragraph case for it and the evidence links; in Out of scope, what you deliberately left for a later pass.
4. Do not change `Last grow:` (that tracks feedback-driven passes). Comment on the project: the feature chosen, the two runner-ups and why they lost.
5. Reply in at most 4 lines: the ticket ID and title.
